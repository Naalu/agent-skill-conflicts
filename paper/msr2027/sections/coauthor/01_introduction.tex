\section{Introduction}
\label{sec:introduction}

Skills are small instruction files that extend coding agents~\cite{anthropicskillsblog}. Each skill carries a name and a short description. When the user asks for something, the agent reads the list of names and descriptions and decides which skill, if any, to load. The main products all select skills this way, and none of them checks whether two entries in the list say the same thing~\cite{claudecodeskills,codexskills,agentskillsspec}. Claude Code's documentation acknowledges the risk: when descriptions are vague or overlap, the agent may load the wrong skill or miss a useful one~\cite{claudecodeskills}.

Skills are also copied heavily. In GitSkills~\cite{gitskills}, half of all occurrences are byte-for-byte copies of a file in another repository, and many repositories keep copies of one skill for several agents: in a sample we measured on GitHub, 14.7\% of project repositories keep skills in two or more agent directories. Software engineering research has long documented what happens to copied code: copies drift, and a fix lands in one copy but not the others~\cite{kim2005genealogies,juergens2009clones}. We expect the same with skills, with one difference. The reader of a stale copy is a language model, not a developer who might notice that something looks out of date.

GitSkills is the natural place to measure this, and we started there. Before counting, we compared a stratified sample of 2,300 repositories with the trees GitHub held for them when the dataset was mined. In project repositories the dataset holds 54.2\% of the skill files that were present throughout its mining window. The cause lies in how files were found: code search returns at most 1,000 results per query, and the dataset's partition by file size cannot split a one-byte range that holds more. Counts of skills per repository taken from the dataset are therefore low, and the question is which conclusions survive.

We study two ways a skill list can go wrong. A \emph{conflicting copy} is a skill whose name appears in two agent directories of one repository with different content, so that, for example, Claude Code and Codex read different instructions under one name. We call such a name \emph{mirrored} and, when its copies differ, \emph{diverged} (Section~\ref{sec:rq1method}). \emph{Competing skills} are two differently named skills in one catalog whose descriptions overlap so much that a realistic request could reasonably go to either. Recent experimental work shows that competition lowers selection accuracy~\cite{li2026singleagent,chen2026scaling,song2026shadowing,yan2026oneskill}, but no study has measured drift between mirrored copies, and the prevalence of competition has not been measured on GitSkills or with human labels and a sampling design. We ask:

\begin{itemize}
\item \textbf{RQ1 (conflicting copies).} How often does a repository give its coding agents different copies of the same skill, and does the answer change when it is measured from the dataset instead of from GitHub?
\item \textbf{RQ2 (competing skills).} How often do differently named skills in one catalog compete?
\end{itemize}

Our contributions are (1) a design-based estimate of how much of each repository GitSkills holds, the mechanism behind the gap, and a repair that costs two API calls per repository; (2) RQ1 measured from the dataset and from GitHub for the same 2,083 repositories, which shows that the dataset undercounts mirroring by about a third but recovers the rate at which mirrored copies diverge; and (3) a codebook for competing skills and a reliability study on 180 human-labeled pairs that shows where coders disagree.
